# Публикация и результаты

REELINATOR хранит решения и результаты рядом с исходниками ролика. Агент использует
подключённые инструменты для чтения статистики; собственного API-клиента, фонового
сборщика и универсальной команды analytics в reel.py пока нет. Ручные данные тоже подходят.

## Когда агент предлагает следующий шаг

| Момент | Инициатива агента | Что требует решения пользователя |
|---|---|---|
| Новый стиль для ролика | Короткая проба действия, смены плана и титров в движении | Существенный выбор направления, если ещё не выбран |
| Пользователь принял готовый ролик | Подготовка публикации, если она ещё актуальна | Отправка/публикация |
| Пользователь сообщил «вышел» или прислал показатели | Сохранить запись и предложить получение статистики | Подключение нового сервиса |
| Сервис выбран или подключён | Объяснить разницу между доступом и расписанием, предложить период | Создание/изменение расписания |
| Получен новый замер | Сравнить сопоставимые данные и предложить гипотезу для следующего ролика | Изменение принятого монтажа или стиля |

Текущий запрос и существующие решения приоритетны. Не превращать таблицу в обязательный
опрос или предложение всех услуг при каждом сообщении. Отказ/отсрочку хранить в SOURCE.md;
не повторять предложение без нового основания. Уже разрешённую работу продолжать.

## Записи одного ролика

- SOURCE.md — текущая задача, решения и ссылки на подробные записи; состояние публикации
  и решения о получении статистики/расписании.
- DECISIONS.md — подробные решения и отменённые варианты, если объём требует отдельного файла.
- metrics.json — сведения о публикации и история замеров, создаётся при появлении таких данных.
- RESULTS.md — оценка пользователя, сравнение, гипотезы и ограничения интерпретации.

Не создавать пустую аналитику для каждого черновика. Если нужен общий журнал нескольких
публикаций, он ссылается на проекты, не заменяя их записи. Живые аккаунты, показатели,
материалы и настройки расписаний не включать в публичные примеры репозитория.
Для ролика с привязкой к аккаунту веди такой журнал в `video/accounts/<account>/RESULTS.md`
и связывай его с паспортом этого аккаунта. При первом сохранении результата дай пользователю
ссылки на журнал и запись ролика: ему не нужно отдельно выяснять, где искать статистику.

Минимальная запись (пример структуры без реальных данных):

```json
{
  "publication": {
    "status": "unknown",
    "platform": null,
    "url": null,
    "published_at": null,
    "published_export_run": null
  },
  "snapshots": []
}
```

Для публикации указывай источник подтверждения: сообщение пользователя или ответ сервиса.
Дата сообщения не равна дате публикации. Последний экспорт не обязательно опубликованный.
В снимке сохраняй reported_on/observed_at по доступности, часовой пояс, источник,
период запроса, доступное время обновления сервиса, возраст публикации, значения и единицы.
Неизвестное — null или отсутствующее поле, не 0. Дополнительные поля провайдера допустимы;
существующие записи и пользовательские исправления сохранять.

Для понятных единиц используй имена вроде views, likes, average_watch_time_seconds,
skip_rate_percent. Значение процента 28.8 означает 28,8%, а не 0.288. Если единицы ответа
не подтверждены, сохрани исходное поле/единицы отдельно и не записывай догадку в seconds.
Счётчики saved/shares/reposts и их доли — разные показатели; у расчётной доли укажи
знаменатель. Не вычислять количества из округлённых процентов с неизвестной базой.

## Подключение и выгрузка

Сначала проверь инструменты текущей среды и уже подключённые аккаунты. Если подходящего
подключения нет, найди доступный коннектор и проверь актуальные возможности/стоимость
по документации провайдера. Не обещай конкретные метрики по одному названию сервиса.
Авторизацию проходит пользователь; после неё агент проверяет соцсеть, аккаунт, поля и
реальное чтение. Коннектор, подключённый к пустому кабинету сервиса, ещё не даёт данных Instagram.

Запрашивай нужный период с часовым поясом. При первом чтении учитывай доступную историю
провайдера. Пустой ответ или ошибка сохраняются как статус попытки отдельно от snapshots;
это не нулевая статистика. При первоначальной синхронизации укажи ограничение и следующий
шаг, не объявляй предполагаемую причину установленной. Устаревшие поля API не использовать.

Сопоставляй по ID/URL; первое соответствие по содержимому сохраняй только при однозначной
идентификации. Не создавай дубликат снимка при повторе того же ответа с тем же временем
источника. Если провайдер не отдаёт время обновления, храни время чтения и отмечай это.

## Расписание

Предлагать сбор полезно, но подключение само по себе не разрешает регулярную задачу.
После согласия используй доступный планировщик среды, проверь существующую задачу,
сохрани ID, частоту, время и часовой пояс, статус создания и последнего импорта.
Период выбирается под обновление источника и потребность пользователя, а не универсально.
Если планировщика нет, сообщи, что доступно чтение по запросу, и не обещай фоновую работу.
Условия выполнения локальной задачи проверь для используемой среды и объясни пользователю.

Задание должно читать актуальные записи проекта, добавлять снимки без затирания ручных
данных, отделять пустые ответы от нулей и выдавать результат или причину сбоя. Настройка
расписания не доказывает, что первый импорт уже успешен. Хранить только необходимые
метаданные подключения; секреты и полные ответы с данными аккаунта не сохранять.

## Разбор результата

Сравнивай одинаковые определения метрик, возраст постов и органические/платные данные.
Падение счётчика может быть коррекцией источника; не скрывай его, но и не объясняй причиной
без доказательства. Среднее время / длительность — не доля досмотров. Без кривой удержания
нельзя установить точную секунду ухода. Успех относительно аккаунта и субъективное замечание
к темпу могут быть одновременно верны. Не выдавай один удачный ролик за доказательство
влияния конкретного приёма: сохраняй наблюдение и предлагай следующий сравнимый эксперимент.
